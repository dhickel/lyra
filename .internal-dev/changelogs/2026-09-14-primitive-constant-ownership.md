# Primitive Constant Ownership: Remove LyraType Alias Fields (Issue #13)

## Date

2026-09-14

## Git Commit

58a8a19bde1f28c90368573f27fa990a995f0ec3

## Change Summary

Removed the fourteen primitive constant fields from both `LyraType` interfaces and the four unused capitalized aliases (`Bool`, `Char`, `String`, `Unit`) from both `PrimitiveType` enums. Primitive constants are now owned solely by `PrimitiveType`. This eliminates the unsafe ordering in which a constant field declared on the interface is initialized from the enum that implements it. Mechanism: when `PrimitiveType` initializes, JLS 12.4.2 initializes its superinterfaces that declare at least one default method first (the pre-SE-9/JVMS phrasing was 'at least one non-abstract, non-static method'). The runtime `LyraType` declares `default canonical`, `default spelling`, and `default isNullable`, so it was initialized while `PrimitiveType`'s constant fields were still null and its `I32 = PrimitiveType.I32` field initializer stored null. The compiler `LyraType` declares only abstract methods, so enum-first initialization did not initialize the interface at all: its field initializer ran later against the completed enum and stored the constant, in either order. The compiler fields were removed anyway because their safety depended entirely on that method shape. Measured reproduction of both pre-change shapes is recorded in `.internal-dev/bugs/compiler/lyratype-primitive-init-cycle.md` under Verification Correction (2026-09-14).

Added isolated initialization-order regressions in both modules (a `URLClassLoader` whose only parent is the platform class loader, so parent-first delegation cannot resolve project classes and the classes are defined in the loader): `PrimitiveTypeInitializationTest` loads `LyraType` first and `PrimitiveType` first in a `URLClassLoader` parented to the platform loader, asserts all fourteen constants and their type operations (spelling, primitive/composite/numeric/integer/floating classification, qualifier operations, nilable/mutable wrappers, and the module-specific numeric domain or bit-width/bounds), asserts the loaded classes are the isolated copies rather than the application-loader copies, and asserts the removed alias fields are absent by name.

## Behavioral Impact

Java source and binary compatibility break, intentionally and without a shim: `LyraType.I32`-style references and `PrimitiveType.Bool/Char/String/Unit` no longer exist, so Java consumers must reference `PrimitiveType.I32` and its siblings and recompile. No Lyra source-language behavior, compiler diagnostic, artifact layout, or runtime authority boundary changes.

Recorded correction: the domain validator's BLOCKED finding was that the records overstated a symmetric compiler/runtime hazard. An isolated reproduction of both original shapes confirmed the runtime default-method module observed `null` and the compiler all-abstract-method module did not. The code was correct; the record wording was repaired before the confirmation pass.

Versioning audit: this is not a Lyra source-language, artifact-schema, or runtime-ABI change. No generated bytecode references a `LyraType` or `PrimitiveType` static field (the compiler uses the runtime type model only at compile time and emits no field reference to either class), so `LANGUAGE_CONTRACT_VERSION`, `ARTIFACT_SCHEMA_VERSION`, and `RuntimeAbi.CURRENT` remain `1`, `1`, and `1.0`. Existing artifact metadata/compatibility coverage remains in place and green; `Phase18ArtifactTest` and `NominalArtifactMetadataTest` were migrated to `PrimitiveType` references with their assertions unchanged. The required ABI increment was evaluated and found unnecessary rather than skipped.

## Specification Impact

`backend-runtime.md` Public Java API now states that primitive constants are owned solely by `PrimitiveType`, that the former interface and enum aliases are not restored for compatibility, and that the removal is a Java API break without effect on the source language, artifact schema, or runtime ABI. `decisions.md` records the durable decision, its justification, rejected alternatives, and the accepted break. Neither the source-language contract nor any artifact-identity contract changes.

## Risks

- The removal is a hard break for any external Java consumer of the removed fields. It is deliberate and documented; no repository consumer remained.
- The isolated-loader regression depends on the module's own classes directory being resolvable from the test class path. It asserts the isolated class identity so a future classpath change that silently reuses the application-loader copy fails the test instead of passing vacuously.
