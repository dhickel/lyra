# Editor process and debugger boundaries

Opening a Lyra Editor workspace starts analysis, not program execution. The editor uses compiler lexer, grammar, parser, resolution, and typing phases over immutable buffer snapshots. Open unsaved buffers participate in import analysis, but initializers do not run.

Run and Debug create a fresh Java 25 child process. That process owns the `LyraSession`, initialized modules, live values, and owner thread. The JavaFX process exchanges bounded protocol results and passive source metadata. Live generated objects never cross into the UI process.

After a run target returns, its child session remains available to the bottom REPL. A second Run starts a fresh child and fresh program state. REPL submissions within one run retain initialized storage.

Stop has different meanings by ownership:

- For an editor-owned process, Stop terminates that child, including blocked host I/O.
- For an externally attached application, Stop detaches and leaves the host running.

The editor's JDI debugger applies only to editor-owned debug processes. External REPL attachment does not attach a JVM debugger. Breakpoints and stepping observe actual generated bytecode and its source-line metadata. Tail-call lowering and generated bridges can change visible stops and frames.

The compiler currently emits no local-variable tables, so arbitrary function-body locals are not promised in the debugger. Arguments and available object fields can still be displayed without invoking target methods. Source remains read-only while a debug session is retained so lines cannot drift from loaded bytecode.
